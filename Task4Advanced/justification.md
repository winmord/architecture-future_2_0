# Обоснование событийного подхода vs Camel/DWH

## Текущие проблемы (Camel + DWH)

### 1. Высокая связанность систем

Текущая архитектура с ESB (Apache Camel) создаёт тесную связь между сервисами. Изменение в одном сервисе требует
изменения в шине и всех потребителях. Это приводит к:

- Долгому циклу разработки (от 2-4 недель на внесение изменений)
- Каскадным сбоям при сбое одного из компонентов
- Сложности в добавлении новых бизнес-направлений

### 2. Монолитное хранилище

DWH на MS SQL Server является единой точкой хранения и обработки данных. Это приводит к:

- Конкуренции за ресурсы между аналитикой и операционными системами
- Медленным запросам (отчёты строятся часами)
- Ограничениям масштабирования (вертикальное масштабирование только)

### 3. Пакетная обработка (Batch)

Отчёты обновляются по расписанию (раз в день/неделю). Это приводит к:

- Устаревшим данным в момент принятия решений
- Невозможности реагировать на изменения в реальном времени
- Задержкам в бизнес-процессах

### 4. Сложность добавления новых источников

Интеграция каждого нового источника данных требует:

- Изменения схемы DWH
- Добавления новых ETL-процессов
- Тестирования всей системы целиком

## Преимущества событийного подхода (Event-Driven Architecture)

### 1. Слабая связанность (Loose Coupling)

**Как работает:**

- Домены обмениваются событиями через Kafka без прямой зависимости
- Каждый домен независим в своём развитии
- Изменение в одном домене не влияет на другие

**Пример:**
При добавлении нового типа медицинского исследования не нужно менять финтех-домен. Достаточно опубликовать новое
событие.

**Выгода:**

- Скорость разработки увеличивается в 2-3 раза
- Возможность независимого развёртывания команд
- Снижение рисков каскадных сбоев

### 2. Асинхронность и масштабируемость

**Как работает:**

- События обрабатываются асинхронно
- Каждый сервис масштабируется независимо
- Нагрузка распределяется через партиционирование Kafka

**Пример:**
При наплыве пациентов система автоматически масштабирует медицинский домен, не затрагивая финтех-домен.

**Выгода:**

- Горизонтальное масштабирование до 100+ сервисов
- Утилизация ресурсов до 40-50% (против 70-80% у монолита)
- Отказоустойчивость за счёт репликации

### 3. Near-real-time обработка

**Как работает:**

- События обрабатываются в реальном времени (миллисекунды)
- Витрины данных обновляются потоково
- Отчёты строятся на актуальных данных

**Пример:**
При обработке платежа система сразу обновляет финансовые витрины и доступна для аналитики.

**Выгода:**

- Отчёты доступны с задержкой < 1 секунды (против часов)
- Возможность принятия решений в реальном времени
- Улучшение клиентского опыта

### 4. Простота добавления новых систем

**Как работает:**

- Новые системы подключаются как подписчики на существующие события
- Не требуется модификация существующих доменов
- Используется Schema Registry для обеспечения совместимости

**Пример:**
При добавлении нового фармацевтического партнёра достаточно подписаться на события PrescriptionIssued.

**Выгода:**

- Интеграция новых систем за 1-2 дня (против 2-3 недель)
- Возможность экспериментировать с новыми сервисами
- Снижение времени вывода продуктов на рынок (Time-to-Market)

### 5. Отказоустойчивость

**Как работает:**

- События хранятся в Kafka до обработки всеми подписчиками
- Недоставленные сообщения попадают в DLQ
- Автоматический ретрай при сбоях

**Пример:**
При сбое аналитического сервиса события не теряются и будут обработаны после восстановления.

**Выгода:**

- Гарантированная доставка событий (at-least-once / exactly-once)
- Снижение потерь данных до 0%
- Возможность восстановления после сбоя без потери транзакций

### 6. Отказ от DWH как источника истины

**Как работает:**

- Каждый домен хранит свой источник истины (source of truth)
- DWH становится аналитическим хранилищем, а не операционным
- Данные синхронизируются через события

**Пример:**
Медицинский домен хранит полную историю пациента, а DWH использует агрегированные данные для аналитики.

**Выгода:**

- Снятие нагрузки с DWH
- Возможность независимого развития аналитики
- Снижение стоимости хранения данных

### 7. Реактивные потоки и масштабирование на 3 года

**Как работает:**

- Архитектура поддерживает реактивные потоки (project reactor, akka streams)
- Обработка событий в реальном времени без блокировок
- Масштабирование до 1000+ событий в секунду

**Пример:**
Потоковая обработка финансовых транзакций позволяет выявлять мошенничество в реальном времени.

**Выгода:**

- Готовая масштабируемость для роста бизнеса (новые регионы, новые продукты)
- Переход от batch к real-time аналитике
- Монетизация ИИ-сервисов через реактивную обработку данных

## Сравнительная таблица

| Критерий                  | Текущая архитектура (Camel + DWH) | Целевая архитектура (Event-Driven) |
|---------------------------|-----------------------------------|------------------------------------|
| Время отчёта              | Часы                              | < 1 секунда                        |
| Время вывода продукта     | Месяцы                            | Недели                             |
| Интеграция нового сервиса | 2-3 недели                        | 1-2 дня                            |
| Масштабируемость          | Вертикальная (ограничена)         | Горизонтальная (бесконечная)       |
| Связанность               | Высокая                           | Низкая                             |
| Отказоустойчивость        | Низкая                            | Высокая                            |
| Утилизация ресурсов       | 70-80%                            | 40-50%                             |
| Потеря данных при сбое    | Возможна                          | Исключена                          |

## Заключение

Переход от синхронной интеграции через ESB к асинхронной событийной архитектуре позволяет компании «Будущее 2.0»:

1. **Ускорить разработку** за счёт слабой связанности доменов
2. **Повысить масштабируемость** за счёт горизонтального масштабирования
3. **Обеспечить near-real-time аналитику** для принятия решений
4. **Упростить интеграцию** новых бизнес-направлений
5. **Снизить риски** за счёт отказоустойчивости и гарантированной доставки событий
6. **Подготовиться к росту** до 3+ регионов и 10+ новых продуктов в горизонте 3 лет
